A customer-support agent wired to money

It can issue refunds.
So it must never
issue the wrong one.

Relay reads a customer's real billing records, decides a resolution with an LLM, and runs every money-touching action through a grounding gate and a deny-by-default policy gate before it executes. If an action isn't both authorized and grounded in that customer's own records, Relay escalates to a human with a case file instead of guessing.

§ 01

The metric
everyone games

The hard part of a support agent isn't resolving the easy 80%. It's guaranteeing the dangerous 20% can't blow up: a refund outside policy, the wrong customer's data, a cancellation it had no business making. "Deflection" — simply not reaching a human — quietly counts wrong auto-answers as wins, so it's the wrong thing to optimize. The number that matters is the unsafe-action rate. Relay holds it at zero, enforces it in code rather than in the prompt, and proves it on a suite written specifically to make the agent slip.

§ 02

The pipeline,
literally

The brain only proposes a structured action; it can never reach the billing store. Only the orchestrator executes, and only after both gates allow. Everything else is handed to a person with a case file.

01
intake
A ticket arrives, bound to one customer id.
02
retrieve
Records are pulled scoped to that customer, and nothing else.
03
propose
The LLM returns a structured proposal. It cannot act on it.
04 · gate
ground
Every cited record must exist and belong to this customer.
05 · gate
policy
Deny-by-default authorization, re-checked against the real records.
06
execute | escalate
Auto-execute, or hand a human the case file.
execute  if  grounding == grounded  and  policy == ALLOW
escalate  otherwise  →  case file + gate code

Then: audit

Every decision is appended to a hash-chained log, redacted so no personal data lands in it. Anyone can re-verify the whole history with relay verify-chain.

Then: respond

The customer gets a real resolution, or a clean handoff to a human. Relay does not answer when it isn't sure it's right.

§ 03

Why it's safe
even when wrong

The brain can be naive, mistaken, or prompt-injected, and the system stays safe, because the guarantees don't live in the model. They live in two plain Python functions the model can't talk its way past.

The model proposes;
it never executes.

Only the orchestrator's execute path calls a money-moving store method, and it runs only after both gates allow. Naive, wrong, or prompt-injected, the model still can't reach the billing store on its own.

Authorization lives in code,
not in the prompt.

Refund caps, eligibility windows, and ownership are a pure, deterministic, deny-by-default function with no else: allow. No instruction smuggled into a ticket body can change a limit that's enforced in Python.

Ground every claim
before policy sees it.

A separate grounding gate rejects any proposal that cites a record which doesn't exist or belongs to another customer — before the policy gate or the store ever run.

Per-customer isolation,
checked twice.

Retrieval is scoped to the ticket's customer id; the grounding gate then independently re-verifies ownership of every cited id. One scope, two checks.

The audit log
proves itself.

Append-only and hash-chained, redacted deny-by-default so no personal data is stored. Anyone can re-derive the chain and confirm nothing was edited after the fact with relay verify-chain.

relay/policy.py · decide() — abridged 
def decide(action, ctx) -> GateDecision:
    if isinstance(action, EscalateAction):
        return _allow("escalate_requested", ...)   # a human asked; always safe
    if ctx.config.sensitive_topics_escalate and ctx.sensitive_topic:
        return _escalate("sensitive_topic", ...)    # dispute / legal / distress
    if ctx.confidence < ctx.config.min_confidence:
        return _escalate("low_confidence", ...)
    if isinstance(action, AnswerAction):
        return _allow("answer_ok", ...)            # informational, no state change
    if isinstance(action, RefundAction):
        return _decide_refund(action, ctx)        # cap, window, ownership — in code
    if isinstance(action, CancelAction):
        return _decide_cancel(action, ctx)
    return _escalate("unknown_action", ...)     # No else: allow.

§ 06

What the numbers
do and don't claim

The guarantee is about the action layer, not the model's answer text. Swap in a real LLM and accuracy drops below 100% while deflection rises above resolution. The unsafe-action rate stays 0, because the gates enforce it and the model doesn't.

unsafe_action_rate == 0  — the real claim

Guaranteed by the gates, and confirmed on a suite built to try to make the agent act unsafely.

accuracy == 100%  — not impressive alone

The reference brain is deterministic and the labels encode its correct behavior. This means "no gate regressed," not that a real LLM is always right.

auto_resolution ≈ 23%  — honest, conservative

The reference brain escalates whenever it's unsure, and the suite is adversarial-heavy. This is not a deflection benchmark.

deflection == resolution  — shown on purpose

On the deterministic brain, deflection (23.44%) equals resolution. It's the vanity metric, kept on the page so it can't be mistaken for the win.
